## Phase 9: FastAPI Service

Ye phase bohat exciting hai — yahan hum apne model ko **"zinda" (live)** kar denge, taake koi bhi **internet ke zariye** usay istemal kar sake, sirf Python script chala kar nahi.

---

## Maqsad Kya Hai?

Abhi tak humara model ek **file** hai (`churn_pipeline.joblib`) jo sirf Python script se load ho sakta hai. Lekin asal duniya mein, koi **website, mobile app, ya doosra system** isay seedha "Python file" ki tarah istemal nahi kar sakta.

**Hal: API (Application Programming Interface) banana.** Ye ek **"darwaza"** hai jiske zariye koi bhi (chahe wo Python jaanta ho ya na ho) hamare model se baat kar sakta hai — bas ek **web request** bhej kar.

---

## Misaal Se Samjhein

Socho aapka model ek **expert doctor** hai jo "customer churn karega ya nahi" bata sakta hai. Abhi ye doctor **ek bund kamray mein baitha hai** — sirf Python jaanne wala banda hi us tak pahunch sakta hai.

**API banana matlab hai:** Doctor ke kamray ke bahar ek **reception desk** laga dena. Ab koi bhi (chahe doctor ki zubaan na jaanta ho) **reception par jaa kar** ek form bhar sakta hai ("ye customer ki details hain"), aur **reception** doctor se poochh kar **jawab** de deta hai ("haan, khatra hai" / "nahi, safe hai").

**FastAPI** is "reception desk" ko banane ka Python tool hai.

## Naya Concept: Pydantic Schema kya hai?

Jab koi banda `/predict` ko customer ka data bhejega, humein **pakka yaqeen** chahiye ke wo data **sahi format** mein ho — jaise `tenure` ek number ho, text na ho.

**Pydantic** ek Python tool hai jo **"form ka design"** banata hai — jaise ek **sawalnama (form)** jisme likha ho "yahan sirf number likhein," "yahan sirf 'Yes'/'No' likhein." Agar koi **galat format** mein data bheje, Pydantic **khud hi** usay **reject** kar deta hai, saaf error ke sath — hamare code ko manually har cheez check nahi karni parti.

**Misaal:** Jaise ek application form mein likha ho "Umar: ___ (sirf number)" — agar koi "bees saal" likh de (text mein), form **khud reject** kar deta hai, "sirf number likhein" bol kar.

## `CustomerData` Class — "Form Ka Design"

```python
class CustomerData(BaseModel):
```

`BaseModel` Pydantic ka khaas "parent class" hai — jab koi class isay "inherit" karti hai (yani `(BaseModel)` likhti hai), Pydantic **khud-ba-khud** validation (jaanch-pataal) ki taaqat de deta hai.

### Ek Field Ko Ghor Se Dekhein

```python
tenure: int = Field(..., ge=0, description="Number of months...")
```

Chaliye tod kar samjhein:

- **`tenure: int`** — iska matlab hai "ye field zaroor ek **number (integer)** honi chahiye." Agar koi `tenure: "barah"` (text) bheje, Pydantic **khud reject** kar dega.
- **`Field(...)`** — ye teen chootki (`...`) batati hai "ye field **zaroori (required)** hai" — yani agar customer data bhejte waqt ye field **chhoot** gayi, request reject ho jayegi.
- **`ge=0`** — ye matlab hai **"greater than or equal to 0"** — yani `tenure` **manfi (negative)** nahi ho sakta. Agar koi `tenure: -5` bheje, reject ho jayega (bilkul theek hai, kisi ka tenure manfi nahi ho sakta!)
- **`description="..."`** — ye sirf ek **tashreeh (explanation)** hai jo `/docs` page par dikhayi degi, taake koi bhi samajh sake ye field kya hai

---

## Ek Dilchasp Baat: `SeniorCitizen` mein Do Hadien (Bounds)

```python
SeniorCitizen: int = Field(..., ge=0, le=1, ...)
```

- **`ge=0`** = kam se kam 0
- **`le=1`** = zyada se zyada 1 (**"less than or equal to 1"**)

**Matlab:** Ye field **sirf 0 ya 1** ho sakti hai — koi aur number (jaise 5) **automatically reject** ho jayega. Ye bohat smart hai, kyunke `SeniorCitizen` ek "binary" (haan/nahi) cheez hai, isay 0/1 tak mehdood rakhna **ghalat data se khud bacha leta hai**.

---

## Ek Zaroori Faisla: `TotalCharges` ko "string" kyun rakha?

```python
TotalCharges: str = Field(..., description="Total charges amount (kept as string for preprocessing pipeline to handle empty strings)")
```

Yaad hai Phase 4 mein humne seekha tha `TotalCharges` **asal mein text (string)** ki shakal mein aati hai, aur kabhi kabhi **khaali** hoti hai? Humari **pipeline khud hi** ye cleaning karti hai (`clean_totalcharges`).

**Agar hum yahan `TotalCharges: float` likhte**, to agar koi khaali ya ajeeb value bheje (jaise `""`), Pydantic **foran reject** kar deta — hamari pipeline ko **mauka hi nahi milta** apni "cleaning" karne ka.

**Isliye ye ek soocha samjha faisla hai:** Hum yahan "loose" validation rakh rahe hain (`str`), taake asal "cleaning" ka kaam **hamari apni pipeline** kare, jo humne Phase 4 mein bohat mehnat se banayi thi.

## `PredictionResponse` Class — "Jawab Ka Design"

```python
class PredictionResponse(BaseModel):
    churn_probability: float = Field(..., ge=0, le=1, ...)
    churn_prediction: str = Field(..., ...)
    threshold_used: float = Field(..., ge=0, le=1, ...)
```

Ye batata hai **API wapas kya dega:**
- `churn_probability` — asal number (jaise 0.65), **0 aur 1 ke beech** mehdood (kyunke probability kabhi 1 se zyada ya 0 se kam nahi ho sakti)
- `churn_prediction` — seedha "Yes"/"No" jawab
- `threshold_used` — ye batata hai **kaunsa threshold (0.3)** istemal hua, taake koi confuse na ho "ye 50% wala rule hai ya 30% wala"

**Faida:** Jab koi API ka jawab dekhega, usay **sab kuch saaf** milega — sirf "haan/nahi" nahi, balke "kitna chance tha" aur "kis rule se faisla hua."

## Naya Zaroori Concept: Model Ko "Baar Baar" Load Na Karna

Agar hum **har request par** model ko dobara load karte (file se parhte), to ye **bohat slow** ho jata — kyunke file se parhna waqt leta hai.

**Behtar tareeqa:** Model ko **server shuru hote waqt, sirf EK dafa** load karein, aur phir usay **memory mein rakh lein**. Jab bhi koi request aaye, **wahi pehle se load hua model** istemal ho.

**Misaal:** Socho ek dukaan hai. Agar dukaandar **har customer ke liye** gudaam (warehouse) jaa kar saman laaye, bohat slow hoga. Behtar hai **subah ek dafa** saman counter par rakh le, phir **sab customers** usi se khareedari karein.
